Resume generation workflow

Draft · 2026-11-23 · Design of the six steps: ingest, distill, verify, to-resume, review-resume and steer. Each step's full rules are in its skill under .claude-dev/skills/; how to run them is in the user manual.

Overview

Six steps, each a Claude Code skill in the resume-evidence plugin. Steps 1–3 turn raw work data into evidence: one anonymised, cited Markdown file per project. Steps 4–5 turn evidence into a resume: YAML that Typst typesets into a PDF, then a review of that PDF. Step 6 lets the user steer the resume directly: the user names the change, and evidence backs or corrects each work claim. Each step reads only what the step before it wrote.

Highlighted nodes are data; plain nodes are steps. Evidence is the hinge. Verify writes back into the same file distill wrote, and to-resume reads only evidence: never raw/, memory or an old resume. A new fact the user gives at step 4 goes back through verify into evidence first. Steer is how the user drives the resume after that: user facts (sections, education, personal projects) go straight into the YAML; each work claim is graded backed, stretched or unbacked against evidence, and an unbacked one is recorded in evidence with a [me: …] citation before it reaches the YAML.

The pipeline also learns as it runs. When the user steers or corrects any step, Claude records the preference in wiki/me.md (gitignored, loaded by CLAUDE.md each session). A lesson that would help any user goes into the skill or reference file it belongs to. Every skill ends with a Learn step that applies .claude-dev/reference/learning.md; scripts/me.py writes the bullets.

Clones sit under repos/, so no project id can collide with jira/ or a file the scripts write. Only raw/ holds real client names; everything committed is anonymised.

    internal_name: <real name> # stays in raw/; never appears in evidence/
    title: <anonymised name>
    sources:
      - url: <git repo url>    # its last segment is the real repo name, banned in evidence/
        slug: <role>          # anonymised repo name: clone folder, citations, verified:
    jira:                      # optional: where its tickets are
      - project: <KEY>         # every ticket in a Jira project
      - project: <KEY>         # only the tickets under one epic
        epic: <epic title>

The user picks each slug once, by the repo's role: backend, worker, detection-lib. It is lowercase kebab-case and unique within its project. Every distill run then cites the repo by the same name, and an update run finds the clone its verified: sha belongs to. The user owns mapping.yml: when a step needs a change, it tells the user what to change.

1 · Ingest

Copies data; reads nothing for meaning.

  1. Check the config. Every project has id, internal_name, title and sources; every source has a url and a slug. A missing field stops the step.
  2. Load repository data. scripts/ingest_repos.py clones each source into raw/<company>/repos/<id>/<slug>/, or fetches it and fast-forwards the checked-out branch, since a fetch moves only the remote branches. A failed clone is recorded, and the run continues.
  3. Count my commits. On every branch, matched against me. commit-summary.json records per repo: load status, my commit count and date range, and branches_ahead: the remote branches holding my commits the checked-out branch lacks.
  4. Load Jira data. If jira: is set, scripts/ingest_jira.py downloads all tickets assigned to me, through the REST API or from Atlassian MCP search results, into jira/<yyyy>.json, and merges them into jira/merged.json. Each ticket keeps only key, title, detail, type, status, project, epic, parent, assignee and dates.
  5. Report and update TODO.md. Flag repos with zero commits of mine, repos not fast-forwarded, and Jira projects or epics no project's selectors pick.

2 · Distill

Turns one project's raw data into its evidence file. Git authorship decides what is mine; a ticket shows assignment, not authorship.

  1. Pick the mode. No evidence file: new mode. A file exists: update mode, reading only the commits after its verified: shas. No repos: interview mode, offered when the user has no repo access or the work left no code. Distill interviews the user on each responsibility, writes each one as a What I Did bullet cited [me: yyyy-mm-dd], and skips authorship and the code reading.
  2. Establish authorship. scripts/authorship.py lists my commits on every branch and my share of blame lines per directory. Blame reads the checked-out branch, or the branch holding my work (--ref <slug>=<ref>) when branches_ahead names one. Each area is classed mine, shared or not mine.
  3. Read the sources and Jira. Code, my main diffs, dependency files and docs for the areas that are mine or shared; the tickets from scripts/jira_tickets.py.
  4. Write the evidence file at evidence/<company>/<yyyy>-<id>.md, where yyyy is the year of my first commit. Every What I Did bullet cites its evidence.
  5. Draft the Summary: three to six resume bullets, each with a Remark naming what it traces to and what limits it.
  6. Anonymise and run the banned-term search until it returns zero hits.

3 · Verify

Git told distill what I did; verify asks what it was worth.

  1. Build the question list from Open questions, guessed frontmatter, configured or estimated numbers, bullets with no outcome, and every draft Summary bullet. Questions that decide a bullet come first.
  2. Interview the user in rounds of at most four. "Don't know" is an answer.
  3. Fold the answers in to the evidence sections, each cited [me: yyyy-mm-dd]. An unknown stays under Open questions, dated.
  4. Rewrite the Summary, anonymise, and set reviewed: when the user confirms the file.

Evidence file

---
id: <project-slug>
title: <anonymised name>
company: <company>
period: yyyy-mm ~ yyyy-mm | present
role: <role>
status: shipped | wip | dropped
verified:
  <slug>: <sha>           # last commit read; the next distill starts here
reviewed: yyyy-mm-dd     # set by verify; empty while the Summary is a draft
---

## Summary           # resume bullets + remarks; distill drafts, verify confirms
## Context
## What I Did        # every bullet cites [slug:path 92%], [slug@sha], [KEY-123] or [me: date]
## Numbers           # value | scope | source
## Tools             # tools: … (used) / Studied, not used: …
## Architecture
## Not mine          # parts built by others
## Open questions

The full schema, Summary rules and anonymisation rules are in .claude-dev/reference/evidence.md.

4 · To resume

Writes the resume's content from evidence. The YAML is the ground truth for the printed resume; Typst only lays it out.

  1. Pick the target. base writes resume/data/resume.yml. A slug such as 2026-dec-acme-ml writes resume/versions/<slug>/resume.yml, with the job ad saved beside it as job-ad.md.
  2. Pick the evidence. Every reviewed file is used. For an unreviewed file the user chooses: verify it first, include its draft bullets, or leave it out.
  3. Fill the facts evidence lacks from the user: employer name, job title, dates.
  4. Plan, then stop. The bullets per job, strongest first; whether each job uses labels, and if so its areas of work, with no two overlapping; for a version, the job ad's requirements sorted Direct, Bridge or Gap; the Remarks that limit each bullet; what to cut to fit maxPages. The user approves the plan before any YAML is written.
  5. Write the bullets by the resume skill: British English, a plain verb first, one result, 25 words or fewer. Each carries a trace comment, such as # evidence/<company>/<file>.md B2, marked (draft) for an unreviewed file.
  6. Write the skills from the evidence tools: lines only.
  7. Search for banned terms from mapping.yml until zero hits.
  8. Check and build. mise -C resume run check validates the YAML against resume/data/resume.schema.json; mise -C resume run build (or version <slug>) compiles the PDF with Typst. The build fails past maxPages; the lowest-ranked bullets are cut first.

5 · Review resume

Measures the built PDF and writes an HTML review. Every result is measured, except the career adviser's view and reader impressions, which are labelled as opinion.

  1. Measure. .claude-dev/skills/review-resume/measure.sh builds and measures the PDF; resume/review/scripts/line_lengths.py charts line lengths.
  2. Read every page image, the YAML, the job ad, and the evidence file behind each trace comment.
  3. Judge every check, evidence traceability first: trace comments, claims, numbers, review state, skills, banned terms. Then screening, CV standards, readability, format, ATS, contrast and accessibility.
  4. Write resume/review/<slug>.html: score cards, a summary table, the adviser's view, one section per check group, and fixes ranked most important first.

Fixes the user accepts go back into the YAML through to-resume, or into evidence through verify when they change a fact.

Scripts

The LLM writes scripts as it needs them, rather than to a fixed list up front. Scripts read paths and credentials from raw/<company>/mapping.yml, never from hard-coded values, so they hold no client names and are safe to commit.
