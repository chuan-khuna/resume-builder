User manual: from repositories to a reviewed resume

2026-11-23 · For the user who runs the pipeline in Claude Code · Design: Resume generation workflow

Overview

This project turns your work history into resume bullets you can defend. You give it a configuration file for one company. The LLM then loads your repositories (or interviews you, when there are none), writes one evidence file per project, and interviews you to confirm the Summary. Last, it writes the resume YAML from the evidence files and reviews the built PDF. Every resume bullet traces to a cited claim in an evidence file.

Fastest way to a resume: edit the resume directly. You need no skill and no evidence file for this.
  1. Write the content in resume/data/resume.yml: header, skills, experience, projects, education.
  2. To change the layout, edit a template in resume/templates/: classic.typ or rail.typ.
  3. Build the PDF: mise -C resume run build.
  4. Open resume/build/base/classic.pdf.
raw/ and evidence/ are reference data for you: what you did, with proof. Read them to find and check your claims, or type /resume-evidence:steer to get suggestions backed by them. Steps 1–5 below build that reference data.

Before you start

The plugin holds the eight skills.

  1. Open a terminal at the repository root.
  2. Install the pinned tools: mise install.
  3. Check the tools: uv --version and claude --version.
  4. Install the Python dependencies: uv sync.
  5. Install the plugin for this repository: mise run plugins.
  6. Start Claude Code: claude.
  7. Type /resume-evidence and make sure the eight skills appear: ingest, distill, verify, to-brag, to-resume, steer, resume, review-resume.

To try the plugin for one session without installing it, start Claude Code with claude --plugin-dir ./.claude-dev.

If you change a skill file, run claude plugin marketplace update resume-builder-local.

How to prompt

The LLM runs a skill only when you type its command. A request in plain words, such as "distill my project", does not start the skill. Write the command first, then its arguments, then any context in plain words on the same message:

/resume-evidence:<skill> <arguments> <context for the LLM>

Context helps the LLM ask fewer questions: what you know about the project, what to focus on, what to leave out. Each step below gives example prompts. Replace company-a and retail-shelf-cv with your own company slug and project id.

1 · Configure and ingest

One company has one mapping.yml. It tells the scripts who you are in git, where your repositories are, and how to name each project in public.

Warning: mapping.yml holds real client names and a Jira API token. Keep it under raw/. Git ignores everything in raw/ except the example file.

Write mapping.yml

  1. Pick a short slug for the company, for example company-a.
  2. Copy the example: mkdir -p raw/company-a && cp raw/repository-mapping.example.yml raw/company-a/mapping.yml.
  3. Set company to the slug.
  4. Under me, list every git author name and email you committed with.
  5. If you want Jira tickets, fill in jira. Otherwise, delete the jira block.
  6. Add one entry under projects for each project.
  7. For each project, add one entry under sources per repository: its url, and a slug.
  8. Name each slug by the repository's role, such as backend or worker. Do not use the real repository name.

You can also ask the LLM to do the copy. It copies the example and stops; you fill in the values. The LLM never edits mapping.yml after that. When it needs a change, it tells you what to change.

company: company-a                  # folder name under raw/ and evidence/

me:                                 # how to find your commits
  names: [jane, jdoe]               # case-insensitive, matches as a substring
  emails: [jane@company-a.example]  # case-insensitive, exact

jira:                               # optional
  site: company-a.atlassian.net
  email: jane@company-a.example
  api_token: <token>                # https://id.atlassian.com/manage-profile/security/api-tokens

projects:
  - id: retail-shelf-cv             # slug in paths
    internal_name: Acme Shelf       # real name; never written to evidence/
    title: Retail Shelf Computer-Vision Analytics Platform  # public name
    sources:
      - url: git@bitbucket.org:company-a/shelf-mono-repo.git
        slug: shelf-app             # anonymised repo name: clone folder and citations
    jira:                           # optional: where its Jira tickets are
      - project: SHELF              # every ticket in a Jira project (older projects)
      - project: TT                 # only one epic of a shared project
        epic: Retail shelf
FieldRequiredUsed for
companyYesFolder name under raw/ and evidence/
me.names, me.emailsYesMatching your commits. A missing alias hides commits.
jiraNoDownloading the tickets assigned to you
projects[].idYesPaths: raw/<company>/repos/<id>/ and the evidence file name
projects[].internal_nameYesFinding Jira tickets. Banned from evidence.
projects[].titleYesThe anonymised name in the evidence file
projects[].sources[].urlYesThe git URL to clone. Its last segment, the real repository name, is banned from evidence.
projects[].sources[].slugYesThe repository's anonymised name: its clone folder, and its name in evidence citations and verified:. Lowercase kebab-case, unique within the project.
projects[].jiraNoSelectors that pick the project's tickets: {project: X} for a whole Jira project, {project: X, epic: Y} for one epic. Ingest tells you which to add.

Example prompts: configure

/resume-evidence:ingest company-a

Check raw/company-a/mapping.yml before you clone. List each field that is
missing or still holds an example value.

I committed with two identities: my work email and my personal one. Tell me
which repos show zero commits from either.

Run ingest

  1. In Claude Code, type /resume-evidence:ingest company-a.
  2. Wait for the report. It shows one table per project.
  3. For each repository marked failed, fix the URL or your git access.
  4. For each repository with zero commits of yours, add the missing name or email to me, or fix the URL.
  5. If you changed mapping.yml, run ingest again.

Ingest only copies data. It checks that every source has a url and a slug, then clones each source into raw/<company>/repos/<id>/<slug>/, or fetches it and fast-forwards the checked-out branch if it is already there. It writes your commit counts to raw/<company>/commit-summary.json, with the branches that hold commits of yours the checked-out branch lacks, and your Jira tickets to raw/<company>/jira/<yyyy>.json, merged into raw/<company>/jira/merged.json. Each ticket keeps only its key, title, detail, type, status, project, epic, parent, assignee and dates. With an API token in mapping.yml, the script downloads the tickets. Without one, the LLM uses the Atlassian MCP if it is connected. A Jira project with your tickets but no entry in mapping.yml goes into TODO.md as a project to add. You can run ingest again at any time to pick up new commits.

You can also run the scripts yourself:

uv run scripts/ingest_repos.py company-a   # clone or fetch the repos, count your commits
uv run scripts/ingest_jira.py company-a    # download your Jira tickets (needs jira.api_token)
uv run scripts/jira_tickets.py company-a retail-shelf-cv   # one project's tickets
uv run scripts/jira_tickets.py company-a --unmapped        # tickets no project selects
uv run scripts/my_commits.py company-a                     # your commits as CSV, in raw/company-a/

2 · Distill

Distill reads one project's raw data and writes its evidence file: what you did, with a citation for each claim, and no real names. Run it once per project.

  1. Type /resume-evidence:distill company-a retail-shelf-cv.
  2. If you leave out the company or the project, pick one from the list the LLM shows.
  3. Wait while the LLM measures your authorship, reads the code and reads the tickets.
  4. Read the draft Summary the LLM shows first.
  5. Read the rest of the file and the list of open questions.
  6. If a claim is wrong, tell the LLM what you actually did. It records your answer as a [me: yyyy-mm-dd] citation.
  7. Confirm the file when it is correct.
  8. Review the diff and commit evidence/company-a/<yyyy>-retail-shelf-cv.md.

You do not need to answer every open question here. Verify asks them later.

No repositories: interview mode

Use interview mode for work you cannot ingest, such as a job where you lost repository access.

  1. Add the project to mapping.yml with its id, internal_name and title, and no sources.
  2. Type /resume-evidence:distill company-b ops-dashboard.
  3. When the LLM finds no repositories, choose the interview.
  4. Answer each round of questions: the context, then each of your responsibilities, then outcomes, tools and what held the work back.
  5. Describe each responsibility clearly: what you owned, how you built it, and the trade-off. The LLM sends a vague answer to open questions.
  6. Continue from step 4 above: read the Summary, correct it, confirm it and commit it.

Each responsibility becomes a What I Did bullet cited [me: yyyy-mm-dd]. The year in the file name is the first year of the period you give.

Example prompts: distill

/resume-evidence:distill company-a retail-shelf-cv

/resume-evidence:distill company-a retail-shelf-cv
I joined this project in March 2025, after the first version shipped.
I owned the detection pipeline and the ingestion service. A teammate built
the dashboard, even where my name is on the merge commits.

/resume-evidence:distill company-a
Which projects in mapping.yml have no evidence file yet? Start with the
one where I have the most commits.

What distill writes

The file is evidence/<company>/<yyyy>-<id>.md, where yyyy is the year of your first commit in the project. Its sections:

SectionHolds
FrontmatterTitle, period, role, status (shipped, wip, dropped), the verified: commit read per repo, and reviewed:
SummaryResume bullets grouped by area of work, starred by strength (★★★, ★★, ★), and a Remark for each; a draft until verify
ContextWho the project was for, the problem, rough scale
What I DidOne cited bullet per thing you owned, decided or built
Numbers & ImpactEvery figure once, with its kind, scope and source; and each Impact item: what the work changed, as a fact, an assessment or your account
ToolsTechnology actually used, and what was only studied
ArchitectureA Mermaid diagram and a short explanation
Not mineParts others built, named by role
Open questionsGaps git cannot answer

Citations

FormMeans
[backend:src/api 92%]Your share of the blame lines under that path
[backend@a1b2c3d]One of your commits
[KEY-123]A Jira ticket. Proves assignment, not authorship.
[me: 2026-11-23]Your own account, given on that date

Distill again after new work

  1. Run ingest for the company to fetch the new commits.
  2. Run distill for the same project.

Distill finds the existing file and starts at its verified: commits. It adds new bullets and keeps the existing ones. If the Summary is already confirmed, new bullets are marked (draft). Run verify again to confirm them.

Example prompts: distill again

/resume-evidence:distill company-a retail-shelf-cv
I ingested the commits from the last three months. Add the new work only;
keep the confirmed bullets as they are.

3 · Verify

Git shows what you did. Verify asks you what it was worth: outcomes, scale, whether it shipped. It then rewrites the Summary as confirmed resume bullets.

  1. Type /resume-evidence:verify company-a retail-shelf-cv.
  2. If you leave out the arguments, pick a file from the list. The list shows which files are reviewed and how many open questions each has.
  3. Answer each round of questions. A round has four questions or fewer.
  4. If you do not know an answer, say "don't know".
  5. For each assessed Impact item, confirm it or reject it. A rejected item is deleted; the facts under it stay.
  6. To end the interview early, tell the LLM to stop.
  7. Read the rewritten Summary and the diff of the evidence sections.
  8. Correct anything wrong.
  9. Confirm the file. The LLM sets reviewed: to today.
  10. Commit the evidence file.

Example prompts: verify

/resume-evidence:verify company-a retail-shelf-cv

/resume-evidence:verify
Show me which evidence files are not reviewed yet, and how many open
questions each has.

/resume-evidence:verify company-a retail-shelf-cv
Ask about outcomes first: what shipped, and the numbers. I have the
production latency figures from our monitoring dashboard.

Example answers during the interview:

1. Shipped to production in June 2025; about 300 stores used it.
2. Don't know. The client never shared accuracy in the field.
3. Partly mine: I wrote the model training, a teammate wrote the labelling tool.
4. Don't quote the 0.65 mAP figure. Product AP50 0.92 is fine.

How to give good answers

  • Give numbers with a scope: "p95 latency fell from 800 ms to 120 ms, measured in production over a week".
  • Say if a number is a guess. The file marks it as estimated or user-reported.
  • Say if you only committed work that a teammate designed. Your account overrides git.
  • Say if a feature never shipped. The bullet then reads "prototyped" or "evaluated", not "delivered".
  • Say what held the work back: too little time, a skill you lacked then, low interest. The LLM records it in your private note, never in the evidence file.
  • Use real names in answers if you need to. The LLM anonymises the file and runs the banned-term search before you confirm.

Each answer goes into the evidence sections first, cited [me: yyyy-mm-dd], and only then into a bullet. A "don't know" stays under Open questions with the date you were asked. If an answer names a repository or Jira project not in mapping.yml, the LLM tells you what to add and records it in TODO.md.

Use the result

Pick bullets from ## Summary for your resume. They are grouped by area of work; start with the ★★★ ones. Read the Remarks before you choose: each one names the claim the bullet traces to, the numbers and impact it uses, its caveat and the roles it fits. Leave out any impact that is still assessed: confirm it in verify first.

4 · Write the resume

The resume lives in resume/. Its content is one YAML file: resume/data/resume.yml for the base resume, or resume/versions/<slug>/resume.yml for one job application. Work bullets and skills come only from evidence files. Your name, contact details, employers, job titles, dates and education come from you.

  1. Verify every evidence file you want on the resume.
  2. For the base resume, type /resume-evidence:to-resume.
  3. For one job application, type /resume-evidence:to-resume 2026-dec-acme-ml, and paste the job ad when the LLM asks.
  4. If the LLM lists unreviewed evidence files, choose: verify first, include as draft, or leave out.
  5. Give the employer name, job title and dates for each company when the LLM asks.
  6. Read the plan. Approve it, or tell the LLM what to change.
  7. Read the YAML diff and the page images in resume/build/<slug>/.
  8. Correct any bullet you cannot defend in an interview.

Each bullet in the YAML has a trace comment above it, such as # evidence/company-a/2025-retail-shelf-cv.md B2. It names the evidence file and the Summary bullet the claim comes from. Keep the comment when you edit the bullet. To reword text without the full pipeline, use /resume-evidence:resume.

/resume-evidence:to-resume

/resume-evidence:to-resume

keep computer vision as supporting work. Fit one page.

/resume-evidence:to-resume 2026-dec-acme-ml

/resume-evidence:resume

Example answers when the LLM asks for facts that evidence does not hold:

To build the resume yourself:

mise -C resume run check            # check the YAML against the schema
mise -C resume run build            # base resume -> resume/build/base/classic.pdf
mise -C resume run version <slug>   # a version   -> resume/build/<slug>/classic.pdf
Warning: the build fails if the resume runs past maxPages (default 1). Cut or hide bullets before you raise maxPages.

Write a brag document (optional)

A brag document holds all your work at one company in a form you can read in one sitting. Use it to prepare for interviews and reviews, or to write a cover letter. The resume keeps a few bullets; the brag document keeps the rest, grouped by theme across projects. It does not feed the resume.

Warning: do not edit brag-document.md by hand. The next run replaces it. Change the evidence through verify or steer instead.
  1. Verify the evidence files of the company first.
  2. Type /resume-evidence:to-brag company-a.
  3. If you leave out the company, pick one from the list the LLM shows.
  4. Open evidence/company-a/brag-document.md.
  5. Read the themes and the interview stories.
  6. Read the Not yet confirmed section.
  7. For each claim under Not yet confirmed, run /resume-evidence:verify on its evidence file.
  8. If a claim is wrong, correct its evidence file through verify or steer.
  9. After each change to the evidence, run to-brag again.
  10. Commit the brag document when it is correct.

Each line cites the evidence file and the IDs it comes from, such as B2 or N1. A line from an unreviewed file is marked (draft). An assessed Impact item appears only under Not yet confirmed. No skill uses the brag document to back a resume claim.

SectionHolds
At a glanceThree to five sentences: what you did, the main themes, the strongest results
ThemesEvery Summary bullet of the company, under one theme each, starred by strength
TimelineOne row per evidence file, newest first: period, project, role, status, headline
Beyond the codeTeam enablement, knowledge transfer, rescues, governance, adoption and avoided waste

Interview storiesThree to six projects as situation, task, action and result

5 · Review the resume

  1. Type /resume-evidence:review-resume for the base resume, or /resume-evidence:review-resume <slug> for a version.
  2. Open resume/review/<slug>.html in a browser. The base resume writes index.html.
  3. Fix every fail row first. Start with the Evidence traceability group.
  4. Apply the fixes you agree with through /resume-evidence:to-resume or /resume-evidence:steer.
  5. Run the review again.

The review measures the PDF for screening, CV standards, readability, format, ATS, contrast and accessibility. It also checks that every bullet has a trace comment, claims no more than its evidence, and quotes only numbers from the evidence.

Example prompts: review

/resume-evidence:review-resume

/resume-evidence:review-resume 2026-dec-acme-ml rail
Compare the rail template with classic for this version. Focus on the
keyword match with the job ad.

/resume-evidence:to-resume 2026-dec-acme-ml
Apply fixes 1 to 3 from resume/review/2026-dec-acme-ml.html. Skip fix 4:
I keep the projects section.

6 · Steer the resume

Use steer to change the resume yourself: sections, their order, a project, an education line, or the experience bullet you want to write. The LLM checks each work claim against the evidence and suggests wording the evidence supports.

  1. Type /resume-evidence:steer, then the change you want. Add a slug to change a version.
  2. Read the grade of each work claim: backed, stretched or unbacked.
  3. For a stretched claim, choose the suggested rewrite or leave the claim out.
  4. For an unbacked claim, give your account to record in evidence, or leave the claim out.
  5. Read the page images and the YAML diff.

Sections, education, activities, interests and personal projects need no evidence. A claim about your work always traces to an evidence file. If no evidence file fits, run /resume-evidence:distill in interview mode first.

Example prompts: steer

/resume-evidence:steer
Put Projects above Experience, and hide the POS rewrite project.

Add a bullet: "Led the move from Kafka to RabbitMQ, cutting failed jobs by half."

/resume-evidence:steer 2026-dec-acme-ml

How the pipeline learns your preferences

Every skill ends with a Learn step. When you steer, correct or reject something, the LLM records it as a dated bullet in wiki/me.md. wiki/me.md is gitignored, and CLAUDE.md loads it in every session, so later runs follow it. A lesson that helps any user goes into the skill itself, and the LLM tells you what it changed.

  1. To read your preferences, run uv run scripts/me.py show.
  2. To add one yourself, run uv run scripts/me.py add preference "<text>".
  3. To change or delete one, edit wiki/me.md.

Wiki

wiki/ is a knowledge base the LLM writes for you: job ads, companies, technologies, articles and talks you want to remember. You add sources and ask questions; the LLM writes and links the notes. Open wiki/ as an Obsidian vault to browse them. A wiki note never backs a resume bullet; only evidence does. Notes are committed, so they never hold client names, credentials or anything else from raw/; lint fails on any term from your mapping.yml files. The rules are in wiki/CLAUDE.md.

  1. Save a source to wiki/raw/ as <yyyy-mm-dd>-<slug>.<ext>. The LLM never edits this folder.
  2. Type /resume-evidence:wiki ingest. The LLM tells you the key points; say what to emphasise.
  3. To ask a question, type /resume-evidence:wiki query, then the question. Keep a good answer as a note.
  4. From time to time, type /resume-evidence:wiki lint to find contradictions, orphans and gaps.
uv run scripts/wiki.py pending   # sources not yet ingested
uv run scripts/wiki.py lint      # broken links, index gaps, bad frontmatter, sensitive terms
grep -h '^## \[' wiki/logs/*.md | tail -5   # the last five log entries

Glossary

Authorship
Your share of a repository, per directory: your commit count and your share of git blame lines at HEAD. Distill claims only paths where your share is real.
Banned-term search
A grep of the evidence file for every real name: internal names, repo names, hosts, the Jira site, clients and people. It passes at zero hits.
Brag document
evidence/<company>/brag-document.md: a readable account of all your work at one company, grouped by theme, that to-brag builds from the evidence files. A view of the evidence, never a source: no resume claim traces to it.
Evidence file
The anonymised, cited record of one project at evidence/<company>/<yyyy>-<id>.md. The ground truth for every resume claim.
mapping.yml
The configuration for one company at raw/<company>/mapping.yml. Only you edit it.
Open question
A gap in an evidence file that git and Jira cannot answer. Verify asks you each one.
Impact item
A row under ## Numbers & Impact → ### Impact in an evidence file: one thing the work changed, such as faster, cheaper, safer, adopted or delivered under a deadline. Its kind is fact (the sources prove it), assessed (the LLM's reading of the facts, usable only after you confirm it in verify) or user (your account).
Plugin
resume-evidence, the local Claude Code plugin in .claude-dev/ that holds the eight skills.
Private note
raw/<company>/notes/<id>.md: the honest account of what held your work back on one project. It stays local and never reaches the resume. It records facts, never blame of others.
Skill
A set of instructions the LLM follows when you type its command, for example /resume-evidence:distill.
Trace comment
A YAML comment above a resume bullet that names its evidence file and Summary bullet, for example # evidence/company-a/2025-retail-shelf-cv.md B2.
Summary
The top section of an evidence file: resume bullets grouped by area of work, starred by strength, with their Remarks. A pool the resume picks from; a draft until verify sets reviewed:.
TODO.md
raw/<company>/TODO.md: projects to add to mapping.yml and leads for distill.
